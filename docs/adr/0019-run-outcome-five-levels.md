# Run Outcome vocabulary spans all five run levels; entry renders every notice

Core modules return a structured Run Outcome and receive an explicit notify adapter for mid-run notices (one-shot, progress handle, clear); every user-facing toast string, display duration, and update cadence lives in entry modules. Toasting directly from core was rejected: bare `toastr` globals bypass the host facade (ADR-0001), retry delays fused to toast lifetimes, and the `''` return collapsed abort, guard block, and failure into one indistinguishable sentinel. Per-call-site toast callbacks were rejected: one notify adapter with a silent test recorder is two real adapters at one seam, testable without DOM or toastr. The adapter instance is created once at the composition root and distributed by argument; core holds no accessor.

**Five levels, six statuses.** The vocabulary is `completed`, `partial`, `aborted`, `blocked`, `failed`, `idle` — `idle` marks no eligible work, `partial` a run that stopped short of its intended work — and it now spans the summarizer request, the batch commit, the promotion drain, the auto cycle, **and the Manual Run**. `partial` is new and the Manual Run is its only producer today: the drain still collapses "committed some promotions, then blocked or failed" into `blocked`/`failed`, and retrofitting that belongs to the auto cycle's terminal handling (it returns the drain's outcome straight through), not to this change. Recorded, not smuggled.

**The Manual Run was the one level without an outcome.** It returned a seven-field flag bag — `cancelled`, `blocked`, `failed`, `completed`, `totalBatches`, `fullyCommitted`, `failureLimitReached` — and entry reconstructed "what happened" twice from different subsets of it: six branches in `showCatchupOutcome`, seven in `showSlopBreakerOutcome`, including shapes like `cancelled && failed > 0` that the bag can express and no notice handles. `runManual` now returns a `ManualRunOutcome`: one status plus the counts its notice is phrased from. State a caller can no longer read is state it cannot re-interpret.

**Reasons are loop state; the verdict is derived once.** The batch loop keeps a tally — counts plus the three reasons it can stop for (`aborted`, `blocked`, `failureLimitReached`) — and one pure `deriveManualRunOutcome(tally, { targetReached, promotionCompleted })` states the precedence that no code previously held: an abort outranks the Foreground Gate, the Gate outranks giving up, giving up outranks progress, and only a run that reached its target with no failures and a drained promotion is `completed`. Consequences of that table: `failed` means the run gave up on three consecutive batch failures (the one error notice — "API may be down" — is selected by it and nothing else), `partial` means it stopped short for any other reason, and `idle` means it neither committed nor failed a batch. A run that reaches its target but had a failed batch is `partial`, where the old `totalBatches > 0 && failed === 0` branch called it "Catch-up complete!" — that notice was wrong about a run that had failed work in it. Threading `status` assignments through the four sites that know a reason was rejected: each site would hold one slice of the precedence, which is exactly the copying ADR-0018 removed one layer up. Deriving the status from `fullyCommitted` was rejected: two fields would answer "what happened", and the count-based notices would have to re-implement the target test to select themselves.

**Display policy belongs to entry.** `MANUAL_STRATEGIES` shipped `label: 'Processing'`, `title: 'Summaryception Catch-Up'`, and `label: 'Breaking slop'` out of core, against `src/AGENTS.md` ("Keep user-facing text out of feature modules") and the seam above; the same table mixed run mechanics (`buildBatch`, `assessCommit`) with notice text. Entry now owns one strategy view (`manualRunView(strategy)`) holding the progress text and the notice map, core's progress callbacks carry counts only, and `usageLabel` stays in core because it is a usage accounting scope label, not a notice. Notices are a `status → notice` lookup per strategy inside that view: the status picks the notice, the counts phrase it (`totalBatches === 0` separates a gate block that never started from one mid-run; `completed` separates a Slop Breaker that committed nothing from one that committed part of the cut), and a status with no entry stays silent — the same convention the notify adapter already uses for unknown kinds. One `showManualRunIdle(strategy)` renderer serves both the pre-run checks and a run that reported `idle`, so "nothing eligible" has one string and one decision. Sending manual progress through the notify adapter instead of the `onStart`/`onProgress` callbacks was rejected: its progress views have no cancel action and no free-text reword, so the protocol would grow to serve one consumer. Reload after a manual run stays shared behaviour on `status === 'completed'` rather than a per-strategy notice: it is page behaviour, and a per-strategy map would invite a divergence nobody asked for.

Consequences: ADR-0004 is superseded — this document restates its decision whole, including the rejected alternatives that still govern. The auto cycle keeps treating anything but `completed` as terminal, and the drain's collapse is unchanged. Entry no longer imports an outcome type from the engine for its notices: `ManualRunOutcome` and the derivation live in `src/core/run-outcome.js` beside the shared typedef, narrowed to the counts a manual notice reads. `CONTEXT.md` Run Outcome covers five levels and `partial`; Operation Mode (ADR-0018) is untouched.
