# Continuity Checkpoint: payload in message extra, latest wins

> Supersedes ADR-0007, ADR-0010, ADR-0011, ADR-0012, and ADR-0013 (2026-09-20).
> This document restates the complete current decision, including the rules
> that previously survived only inside superseded or amended files.

A successful audit writes the merged Continuity State JSON directly into the audited reply's `extra.summaryception_continuity` — the payload is the state object itself, no wrapper, no `audited_sc_id`, no reply-text hash. The live read model is one descending walk over assistant messages (`findLiveCheckpoint`, src/foundation/continuity.js): the newest message carrying a payload wins — no chain walk, no hash comparison, no "strictly before the most recent user message" bound. A newer audit overwrites the payload in place, so swipe, continue, regenerate, and edit need no invalidation logic at any layer. One shared read function serves both consumers: the Auditor's coverage anchor and the prompt injection (src/features/continuity-injection.js).

When a host generation starts with type `swipe` or `regenerate` (`GENERATION_STARTED` args), the live checkpoint is dropped when it sits on the last assistant message (`discardRegeneratedCheckpoint`, src/core/continuity-runner.js) and the injection slot refreshes before the prompt freeze locks the slot content. The read model falls back to the prior checkpoint — the state as of before the rerolled answer — and the regenerated reply becomes unaudited, so the next settled audit re-covers it through the Catch-up Window. The drop is in-memory only: ST persists the chat when the regenerated reply settles. `continue` keeps its payload, because the message stays in the prompt mid-generation; a payload left by an external edit is overwritten by the next audit; an audit settling exactly while its own target's reroll starts can re-attach the stale payload, and the next reroll drops it again.

The Continuity Engine has no swipe semantics anywhere: `isAuditorTriggerMessage` accepts only the `normal` event, and audits fire on settled replies only. The audit is one LLM call: a draft that fails `classifyContinuity` validation writes no checkpoint, and the next audit re-covers the Exchanges through the Catch-up Window (four Exchanges). Staleness is derived, not stored: the injected block shows the stale marker whenever the newest checkpoint's Exchange trails the chat's last Exchange, computed from assistant-message counts.

The runner keeps two non-content guards: the audited reply must still be present in the current chat at settle (reference check; a mid-flight deletion drops the write as `aborted`), and the chat-switch identity guard around the host's `saveMetadata` wait stays. There is no in-flight abort at generation start: ST's `generateRaw` takes no AbortSignal (src/core/connection-default.js), so aborting never saved tokens on the default route, and ST's global `GENERATION_STOPPED` broadcast killed default-route audits collaterally anyway (verified against ST script.js:3946-3959) — audits always run to completion and attach at settle. Everything identity-related left the audit path: no sc_id backfill, no settle-time sc_id re-resolution, and story labels switch from `[sc_id]` to chat-index tags. The audit log still reports the audited reply's `sc_id` for greppability; it is diagnostic text, not state.

Rejected alternatives: the shared chat-metadata slot (pre-0010) — deleting an Exchange older than the anchor contaminated the state permanently, because no rewind fired for an anchor that still resolved. The per-message chain with sc_id resolution, FNV-1a reply-text hash, and pre-user anchor bound (ADR-0010, ADR-0011) — the bound nulled the read model at the exact moment the injection refreshed, clearing the slot so the next generation shipped without the Continuity Block (live failure), and the hash broke whenever an external extension rewrote `mes` in memory while the chat file stayed internally consistent; both mechanisms bought nothing under overwrite semantics. Delta chains over checkpoints (ADR-0010) — replay logic and a single corrupt delta poisoning the chain reintroduce exactly the complexity the change removes. Auditing at swipe time (ADR-0007) — burns calls on drafts the user discards. Retrying the Auditor with repair feedback (ADR-0011) — a second call doubles the cost of every malformed draft while the Catch-up Window already guarantees the next audit re-reads the same Exchanges. Special-casing the injection window between an audit's completion and the next user message (ADR-0011) — the difference is invisible to the main model: the prior state describes the reply being replaced, so showing it is more correct, not stale.

Consequences: existing chats with wrapped `{state, audited_sc_id, text_hash}` payloads cold-start (no migration shims per repo rules) — the payload must be the state object itself. Every settled audit leaves a payload on its reply, and older payloads stay as the reroll-drop fallback, so chat files grow by the state size (~1–3 KB) per Exchange, unbounded. A regenerated reply is unaudited from generation start, so the pre-0013 gap — a kept payload anchoring coverage and shipping the discarded draft's own state — does not exist here.

Unchanged by this consolidation: the Catch-up Window (four Exchanges), the single-call audit, the JS flags rulebook (ADR-0006), `classifyContinuity` JSON validation, the trigger filter, Turn Count re-derivation from the chat, and the Auditor's separate connection chain (ADR-0009).
