# 0018 — Operation Mode owns the on/off and complexity axes

Operation Mode is one foundation module (`src/foundation/operation-mode.js`): the single writer of the stored settings trio `uiMode`, `configMode`, `enabled`, and the one place the verdict is read. It exposes intents — `setComplexity('easy' | 'advanced')`, `setEnabled(true | false)`, `selectOff()` — and one read, `readOperationMode(settings)`, returning the two axes (Operation Mode On/Off, Complexity Mode Easy/Advanced) plus the derived `enabled` gate. Panel visibility is not part of the verdict: `entry/ui-view-models.js` gains `buildEnabledContentModel(mode)` and `syncEnabledContent` renders that View Model, so entry keeps rendering and never computing (CONTEXT.md, View Model; ADR-0016, renderer rule).

**Two axes, one stored radio.** The stored `uiMode` carries both axes in a three-value radio (`off | easy | advanced`) while `configMode` remembers the Complexity Mode across an Off period. Before this decision five sites translated that radio into the two booleans independently — the settings radio handler and the enable checkbox handler (src/entry/ui-events.js), the load-time normalizer `normalizeModeSettings`, the renderer's `off ? configMode || EASY : uiMode` formula (src/entry/ui.js), and the Easy guard `settings.uiMode !== EASY` (src/core/request-attempt.js) — each holding a slice of the invariant `enabled === uiMode !== OFF`. The rule already existed in `src/AGENTS.md` ("Operating mode gates runtime behavior. Complexity mode selects the visible panel."); no module held it. `resetSettingsToDefaults` writes `enabled` as a plain default while preserving `uiMode`, so an Off-mode reset leaves the two fields disagreeing until a second `getSettings()` normalize pass restores them — the same invariant, enforced by re-derivation rather than by an owner.

**Stored, not purely derived.** `enabled` stays a stored field. Deriving it on every read was rejected: `getEffectiveSettings` is identity-equal to `getSettings()` outside Off mode (pinned by `tests/state.test.js`), eleven modules read `.enabled` off a settings object, and `#sc_enabled` is declaratively synced from raw settings (`data-sc-setting="enabled"`). A purely derived `enabled` would change that pinned contract, rewrite every reader, and either drop the synced checkbox control or add the stored-value detection the project rules forbid. The module instead becomes the trio's only writer, and the verdict stays the one derivation.

The intent set was chosen over one generic `applyMode({ enabled, complexity })`: each intent is the genuine sub-decision of one axis, whereas a generic apply makes every caller preserve the axis it does not care about — which is exactly how `uiMode = enabled ? configMode || EASY : OFF` came to exist. An entry-only module was rejected: the load-time repair lives in foundation, the invariant gates core and feature behavior, and an entry-only owner leaves `state.js` re-deriving `enabled` at load with nobody accountable. `panels` in the foundation verdict was rejected as a layering violation: the module answers what mode the extension is in, not which DOM regions are visible.

Consequences: one writer for the trio; the Complexity Mode memory becomes legible as "the Complexity Mode to restore"; `syncEnabledContent` becomes a render of `buildEnabledContentModel`; the Easy guard keeps consuming the stored `uiMode` unchanged, as a consumer of the invariant rather than a re-derivation of it; `CONTEXT.md` gains the Operation Mode and Complexity Mode terms.
