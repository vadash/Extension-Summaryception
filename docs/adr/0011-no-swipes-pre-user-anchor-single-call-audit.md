# No swipes, pre-user anchor bound, single-call audit

> Supersedes ADR-0007; amends ADR-0010's read-model sentence.

The Continuity Engine has no swipe semantics anywhere: swipe, continue, and regenerate are not trigger types (`isAuditorTriggerMessage` accepts only the `normal` event), no rewind or anchor bookkeeping fires for invalidated drafts, and the glossary defines an Exchange as one user message plus its completed assistant reply. Invalidation is handled entirely by the read model's pre-user anchor bound: the live Continuity Checkpoint is the newest valid checkpoint whose chat index sits strictly before the most recent user message's index, and a chat with no user message keeps the newest-valid-wins rule. One shared read function (`findLiveCheckpoint`, src/foundation/continuity.js) serves both consumers — the Auditor's coverage anchor and the prompt injection — so a regenerated reply that still carries its own checkpoint is no longer its own anchor: the next audit runs against the pre-user checkpoint and lands a fresh checkpoint on the regenerated reply, and the injection renders the pre-user state until the next user message arrives. The audit also becomes a single LLM call: the section-aware repair round is deleted, and a draft that fails `classifyContinuity` validation writes no checkpoint — the chain continues from the prior anchor, and the next audit re-covers the Exchanges through the Catch-up Window. Auditing at swipe time was rejected in ADR-0007 and stays rejected: it burns calls on drafts the user discards. Retrying the Auditor with repair feedback was rejected because a second call doubles the cost of every malformed draft while the Catch-up Window already guarantees the next audit re-reads the same Exchanges. Special-casing the injection window between an audit's completion and the next user message (where the read model shows the older checkpoint) was rejected because the difference is invisible to the main model — the just-audited state describes the reply being regenerated, so showing the pre-user state is more correct, not stale.
