# Call Profile: per-call policy resolved once at dispatch

Every summarizer call resolves one Call Profile from settings and the call category at dispatch time — prompts, per-route timeouts (hard fallbacks applied at resolve), connection targets (the merge route folded into primary for promotion), health bucket, output guard flags, the human log label, and verbatim provenance — and the resolved value is the only thing the request path consumes (`resolveCallProfile`, src/core/call-profile.js, invoked inside `buildSummarizerPipelineInput`). Distributing the policy across per-module kind branches was rejected: thirteen `kind`/`useFallback` branches across six modules re-derived slices of the same decision and implemented the label switch twice. A two-value interface (policy profile beside raw metadata) was rejected because it kept the mutable metadata bag alive. Per-attempt re-derivation was rejected: the runner mutated the caller's metadata mid-run (`useFallback`, `layer0Repair`), and re-reading the live settings object per attempt let in-flight settings edits change a call's policy between retries — one call keeps one frozen policy; settings edits apply to future calls only. Repair is not policy: an in-series repair retry carries its flag and rejected output on the attempt's round state, while repair payloads that arrive as fresh dispatches (`promotionRepair`) are profile inputs of that dispatch. The profile rides on the completed Run Outcome, whose text already passed output validation under that profile, so callers act on the same resolved policy instead of constructing throwaway metadata or re-validating. Route fallback *decisions* and retry budgets stay per-route in the runner; the profile only carries the per-route policy variants.
